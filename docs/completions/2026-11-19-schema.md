## 2. Method

The schema was **extracted from the live Access database**, not transcribed from the migration plan's abridged DDL.

```
TrainingDatabase.accdb
  ├─ 70 tables enumerated via ODBC GetSchema("Tables")
  ├─ 447 columns read via SELECT * WHERE 1=0 → GetSchemaTable()
  ├─ primary keys inferred from data (uniqueness verified per candidate)
  ├─ row counts captured for all 70 tables (182,947 rows total)
  └─ integrity checks run against live data
```

The plan's §5.2 DDL was used as a **design guide only**. Where it disagreed with reality, the data won — see §3.

## 3. Where reality differed from the plan

These are the corrections the extraction forced. Each is a place where blindly following the plan would have produced a broken or lossy schema.

### 3.1 Column names

The plan's DDL uses descriptive names (`FirstName`, `Email`, `IsBroken`); Access uses terse ones (`FName`, `ParticipantEmail`, `Broken`). The target uses the plan's names, with the legacy name recorded in a comment on every renamed column so the ETL mapping is unambiguous.

| Legacy | Target | Table |
| --- | --- | --- |
| `FName` / `LName` / `MName` | `FirstName` / `LastName` / `MiddleName` | `Participant`, `PresenterStaff` |
| `ParticipantEmail` | `Email` | `Participant` |
| `ComponenetID` *(typo)* | `ComponentID` | `Workshop` |
| `SYID` | `SchoolYearID` | `Workshop`, `Payment` |
| `Max` / `Min` | `MaxEnrollment` / `MinEnrollment` | `Workshop` |
| `Sessions` / `SessionHrs` / `SessionCEUs` | `SessionCount` / `SessionHours` / `SessionCeus` | `Workshop` |
| `Brochure`, `Folder`, `Closed`, … | `IsBrochure`, `IsFolder`, `IsClosed`, … | `Workshop` |
| `WorkshopEvaluations` | `WorkshopEvaluationID` | `WorkshopEvalQuestion` |
| `WorkshopTypeID` *(PK)* | `EvalTypeID` | `ref.EvalType` |
| `CountyTypeID` *(PK)* | `SummaryCountTypeID` | `ref.SummaryCountType` |
| `[Zip Code]` *(space in name)* | `ZipCode` | `ref.ZipCode` |
| `[Receipt#]` | `ReceiptNumber` | `Registration` |
| `[Order]` | `SortOrder` | `ref.Age` |

### 3.2 Type corrections

| Column | Plan said | Reality | Decision |
| --- | --- | --- | --- |
| `Workshop.SessionHours` | `FLOAT` | `Decimal(18,2)`, max 55.00 | **`DECIMAL(18,2)`** — exact, and CEU maths stays correct |
| `Workshop.Virtual`, `In-Person` | "convert to `BIT`; confirm no values other than 0/1" | **12 and 17 distinct values**, range 0–14 | **Kept as `INT`.** The plan's assumption was wrong; converting would have destroyed data |
| `Workshop.TotalRegistrations`, `TotalParticipants` | migrate as stored | `DOUBLE`, drift from reality | **Dropped.** Replaced by `core.vw_WorkshopCounts` |
| `ref.ZipCode` | add `ZipCode` PK | 1,091 rows, only **106 distinct** ZIPs | **Surrogate `ZipCodeRowID`** + non-unique index on `ZipCode` |

### 3.3 Keys

Primary keys were **inferred from data and verified by uniqueness**, not assumed from naming.

- **63 tables** have a clean surrogate PK (verified `COUNT(*) = COUNT(DISTINCT pk)`).
- **`tblWorkshopEvalQuestions`** — the column named `WorkshopEvaluations` looks like a foreign key but is genuinely unique (3,540/3,540). It is the PK, renamed to `WorkshopEvaluationID`.
- **Junction tables** were given composite PKs after verifying uniqueness:
  - `tblSessionParticipants` → `(ParticipantID, WorkshopSessionID)` — 36,686/36,686 unique
  - `tblCommunityEventStaff` → `(EventID, StaffID)` — 620/620 unique
  - `tblTrainingRequestsPayments` → `(TrainingRequestID, PaymentID)`
- **`tblTrainingRequestsScheduled`** — 84 rows but only **81 distinct** `(TrainingRequestID, WorkshopID)`. **No PK declared**; ETL must resolve the 3 duplicates first.
- **`lstNCZipCodes`** — no PK, and a space in the column name. Surrogate key added.

## 5. Deliberate design decisions

### 5.1 Foreign keys are partial

73 FKs are declared, but **`Registration.ParticipantID` and `Registration.WorkshopID` have no FK constraint yet**. The 2+2 orphan rows would block the load. The ETL must quarantine them first, after which the FKs can be added.

`CK_Workshop_Dates` is also **not yet added** — the 9 inverted date ranges must be corrected first.

This is intentional: the schema accepts the legacy data as-is, and constraints tighten once the data is clean. Both are recorded as comments in `schema.sql`.

### 5.2 Staging is generic, not one-table-per-source

The plan sketched `staging.*` as one table per source table, all `NVARCHAR(MAX)`. That would mean 70 tables and 447 columns of DDL that exists only to be thrown away.

Instead there are two tables:

- **`staging.RawRow`** — one row per source row, with `SourceTable`, `SourceRowID`, `RawJson`. Nothing is lost or coerced.
- **`staging.Quarantine`** — rejected rows with a reason.

This keeps the "land everything as text first" property the plan wanted, without the DDL overhead. If per-table staging proves necessary during ETL, it can be generated from the same metadata.

### 5.3 Public-registration columns pre-wired

`Registration.Source` (`Manual` / `Web` / `ESchools`) and `Registration.RegistrationLinkID` were added now, so the feature in [public-registration.md](../features/public-registration.md) does not require a second migration. `audit.PublicSubmission` is created and ready.

`core.WorkshopRegistrationLink` is **not** created yet — it belongs to the Phase 2b workstream and its shape may still change.
